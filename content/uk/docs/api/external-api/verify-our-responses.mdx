## Overview

We won't check that you've verified our responses, but you should do it anyway. All responses from our API are signed; verifying them ensures the responses you receive are valid and untampered, and confirms that your requests reached us successfully.

## Verify the signature in our response

To verify a response, retrieve the public key we signed it with, rebuild the signature base from the response's headers, and check the signature.

### Retrieve our public keys

ClearBank signs endpoint responses using multiple public keys, and we can sign our responses using any valid key. You should verify our response signatures using our public keys' details. You can retrieve our public JSON Web Keys (JWKs) by ID using our Public Key Endpoint:

<EndpointBlock
  type="get"
  title="Retrieve a Public Key by ID"
  endpoints={[
    {
      path: "/authentication/v1/public-keys/{keyId}",
      version: "EXAPIKEYS_1.0.0"
    }
  ]}
/>

In the interest of performance, we recommend you cache these keys and only call the Public Key Endpoint if we sign a response using a key you have not already cached.

### Build the signature base

To verify our response signature you must build our signature base using the composition specified in the response's `signature-input` header. The steps to do this are identical to those used to build the signature base for a request.

Once this has been built, you can then use our public key to verify the signature.

## Headers used for response verification

Our signed responses include the following headers. Use them to rebuild the signature base and verify the signature.

| Header            | Description                                                                                                                                                          |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `signature-input` | Describes how the signature base is composed, including the list of components, the `keyid` of the public key we signed with, the `created` timestamp, and the tag. |
| `content-digest`  | Present when the response has a body. A SHA-256 hash of the response body, encoded as Base64, in the format `sha-256=:{hash-of-body}:`.                              |
| `signature`       | The signature we generated by signing the signature base with our private key, encoded as Base64, in the format `{signature-id}=:{signature}:`.                     |

### Example

A signed response and the signature base you would rebuild from it look like this:

```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Digest: sha-256=:5hAiS5m/HigGV8+1dStqZj1zk1LfoegovJ0bx4Njoqs=:
Signature-Input: sig=("@status" "content-digest");keyid="baa6842f-8939-4d2e-b8f5-ec716c711600";created=1713800893;tag="fapi-2-request"
Signature: sig=:MEUCIQC1d6wC9rc9FCFMa738GbgxbtFFPeWdcRnL0rrfELN2MAIgW8w57eo46Fl29C5CZ6SRAl2ouq9k/jQ79AkiUVI8OsQ=:

{ "message": "hello world!" }
```

```text
"@status": 200
"content-digest": sha-256=:5hAiS5m/HigGV8+1dStqZj1zk1LfoegovJ0bx4Njoqs=:
"@signature-params": ("@status" "content-digest");keyid="baa6842f-8939-4d2e-b8f5-ec716c711600";created=1713800893;tag="fapi-2-request"
```

Retrieve the public key identified by the `keyid` (see [Retrieve our public keys](#retrieve-our-public-keys)), then use it to verify the `Signature` against the signature base you have rebuilt.

## Handling failed signature checks

If an attempt to verify a response signature fails, you should treat the response as invalid and discard it. You should also log the failed signature check for further investigation.

## Operational best practices

You should ensure your system can handle failed signature checks when verifying our responses. This includes implementing retry logic, monitoring for failed signature checks, and alerting the appropriate team should any issues arise.
