## What are webhooks?

When certain events occur, we generate and send a webhook message to your defined URL. You can subscribe to the webhooks you wish to receive, as described in [Set up and test webhook listener URLs](#set-up-and-test-webhook-listener-urls). When you receive a webhook, you must respond to it to confirm receipt.

All ClearBank webhook bodies consist of a `Type`, `Version`, `Payload`, and `Nonce`. The `Payload` parameters vary depending on the webhook.

## Webhook structure

The webhook body contains the following elements:

| Element   | Type   | Description                                                                                                                                   |
| --------- | ------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `Type`    | string | The type of the event.                                                                                                                        |
| `Version` | int    | The webhook version.                                                                                                                          |
| `Payload` | object | Object which contains information related to the webhook.                                                                                     |
| `Nonce`   | int    | Cryptographically secure number generated by ClearBank for every webhook. It is generated randomly and must not be used to detect duplicates. |

All webhooks are also delivered with the following HTTP headers:

| Header                  | Value                                                                                           | Example                                                                                                                                               | Description                                                                                                                                                                      |
| ----------------------- | ----------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `x-webhook-id`          | Guid                                                                                            | `62bd7bd3-b1f9-4771-a4b8-f40751e99427`                                                                                                                | A webhook identifier. This value is not modified on webhooks that are retried.                                                                                                   |
| `x-fapi-interaction-id` | Guid                                                                                            | `e694054e-3c67-4522-8680-572f4a2ddb50`                                                                                                                | An identifier representing a single request to the External Gateway, intended for request/webhook tracing. | `signature-input`       | {signature-id}=({list-of-components});keyid="{key-id}";created={timestamp};tag="fapi-2-request" | sig=("@method" "@target-uri" "x-webhook-id" "content-digest");keyid="scictt:74c509cadc714ca0a7bb9f61f0957c91";created=1740398429;tag="fapi-2-request" | A description of the signature base that is signed to create the signature. ## Handling a webhook

Webhooks sent by ClearBank include the security components needed for you to verify the authenticity of the data they contain. It is important that you use these to verify that each webhook was sent by ClearBank. Subsequently, ClearBank verifies that you have successfully received the webhook, based on your response acknowledging receipt.

The handling of a webhook can be thought of in three parts: **verification, response, and processing**.

### Verification

You need to verify that ClearBank is the true source of the webhook, and that the webhook has not been tampered with.

To verify the integrity of the webhook received from ClearBank:

1. Verify that the `created` timestamp within the `signature-input` header is within 60 seconds of the moment the webhook was received.
2. Verify that the `content-digest` header matches the SHA-256 hash of the webhook body.
3. Get the public key information for the `keyid` specified in the `signature-input` header. This can be retrieved from `GET /authentication/v1/public-keys/{keyId}` (see [Retrieve our public keys](./verify-our-responses#retrieve-our-public-keys)) and should be cached locally.
4. Build the signature base as described by the `signature-input` header. See [Creating the signature base](#creating-the-signature-base).
5. Verify the signature using the signature base and the public key.

### Response

If you are not able to verify the webhook source, you should respond with a reasonable status/error code to signify that the webhook should be treated as failed. See [Response structure](#response-structure) for how to create a webhook response signature.

<Callout colour="blue">
  A webhook response must be sent as fast as possible, with 5 seconds being the maximum. Any response received more than 5 seconds after the webhook was sent is ignored, and the webhook will be considered to have failed.
</Callout>

We will retry webhooks that we are not able to consider successful. Retries are at least 15 minutes apart from the last failure and continue for 24 hours, or until you return a successful response. We err on the side of caution to ensure you have correctly received the webhook. For more information, see [Idempotency](#idempotency).

### Processing

Due to the 5 second timeout window that applies to successful webhook responses, it makes sense to minimise the processing that is done before responding to the webhook. We recommend verifying, queuing, and responding to the webhook synchronously. An internal queuing solution can then handle any further processing asynchronously (including any checks for duplicates).

### Idempotency

We use at-least-once delivery when sending webhooks. This means that, to ensure you have received a webhook, we may send it to you multiple times.

Duplicate webhooks can generally be identified by looking at the `EventType`, `Timestamp`, and `Id` within the payload. If the values are the same, the webhook is a duplicate.

You must be able to handle duplicate webhooks idempotently. This means you should always respond in the appropriate format even if you have detected a duplicated or retried webhook. If you don't, we won't be able to verify that the webhook was successfully received and will therefore retry delivery.

## Digital signatures

We use digital signatures to ensure that the integrity of a request is maintained, so we require and verify signatures on all requests sent to our APIs. We also sign responses from our APIs and our webhooks so that you are able to verify the integrity of the communication originating from us.

Our digital signatures are based on the [FAPI 2.0 Message Signing](https://openid.net/specs/fapi-2_0-message-signing.html) standard, which is based on [RFC 9421 HTTP Message Signatures](https://datatracker.ietf.org/doc/rfc9421/). These standards should be used when working with your digital signatures; this documentation is provided to help you understand them. For details on signing your own API requests, see [Sign your requests](./sign-your-requests).

### Signature input

The `signature-input` uses the following format: `{signature-id}=({list-of-components});keyid="{key-id}";created={timestamp};tag="fapi-2-request"`

For the `signature-id` you want to verify, extract the components identified. Components appear in three different formats:

| Type               | Format                                      | Examples                                        | Description                                                                                                                                                                                    |
| ------------------ | ------------------------------------------- | ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Derived components | `"@derivedComponent"`                       | `"@method"` and `"@target-uri"`                 | Values that can be derived from the request itself. See [Derived Components](https://datatracker.ietf.org/doc/html/rfc9421#name-derived-components).                                           |
| HTTP fields        | `"header"`                                  | `"x-fapi-interaction-id"` and `"x-webhook-id"`  | Identifiers for HTTP headers; the values of these headers represent the value used in the signature base.\* See [HTTP Fields](https://datatracker.ietf.org/doc/html/rfc9421#name-http-fields). |
| Request components | `"@derivedComponent";req` or `"header";req` | `"@target-uri";req` and `"signature-input";req` | Values taken from the original request, used when a response is being signed. See [Request Components](https://datatracker.ietf.org/doc/html/rfc9421#name-signing-request-components-).        |

\*As per the specification, HTTP fields also include trailers; however, we currently only support HTTP headers. If this changes in the future, we will communicate it.

### Creating the signature base

See the [specification](https://datatracker.ietf.org/doc/html/rfc9421#name-creating-the-signature-base) for the full detail.

When calculating the signature base, the components within the `signature-input` are calculated and appended in the order they are received. The signature base format for each line is `"{component-name}": {component-value}`, with each line separated by a newline. Finally, when all components have been appended, add `"@signature-params": {signature-input header value}`.

### Verifying digital signatures

To verify our digital signatures you need to be able to rebuild the signature base, which is the content that we signed using our private keys. You must:

1. Build the signature base.
2. Get the public key linked to the key that signed the webhook.
3. Verify the signature.

## Response structure

Valid webhook responses **must** contain a `200` HTTP status code and the `Nonce` number in the body of the response. We also require the following headers, as part of the requirement that responses are signed:

| Header            | Value                                                                                             | Example                                                                                                                                                                                     | Description                                                                               |
| ----------------- | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `content-digest`  | `{hash-algorithm}=:{hash-of-response-body}:`                                                      | `sha-256=:5hAiS5m/HigGV8+1dStqZj1zk1LfoegovJ0bx4Njoqs=:`                                                                                                                                    | A hashing algorithm (always `sha-256`) and the UTF-8 encoded, hashed response body.       |
| `signature-input` | `{signature-id}=({list-of-components});keyid="{key-id}";created={timestamp};tag="fapi-2-request"` | `sig=(@status "@method";req "@target-uri";req "content-digest" "signature-input";req "signature";req);keyid="13fc07a9-9f62-4bb5-b9cb-3f7cffc896ac";created=1740398429;tag="fapi-2-request"` | A description of the signature base that is signed to create the signature.               |
| `signature`       | `{signature-id}=:{signature}:`                                                                    | `sig=:MEUCIQC1d6wC9rc9FCFMa738GbgxbtFFPeWdcRnL0rrfELN2MAIgW8w57eo46Fl29C5CZ6SRAl2ouq9k/jQ79AkiUVI8OsQ=:`                                                                                    | The Base64 encoded signature created by signing the signature base with your private key. |

In the response `signature-input` we require the following components:

| Component               | Value                   | Example                                                                                                                                                 | Description                                                                         |
| ----------------------- | ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| Status code             | `@status`               | `200`                                                                                                                                                   | The status code of the webhook delivery. This should be `200`.                      |
| Request method          | `"@method";req`         | `POST`                                                                                                                                                  | The HTTP method used by the delivery. This will always be `POST`.                   |
| Target URI              | `"@target-uri";req`     | `https://www.company.com/webhooks`                                                                                                                      | The URI used by the delivery. This is where the webhook was sent to.                |
| Response content        | `"content-digest"`      | `sha-256=:5hAiS5m/HigGV8+1dStqZj1zk1LfoegovJ0bx4Njoqs=:`                                                                                                | A hashing algorithm (always `sha-256`) and the UTF-8 encoded, hashed response body. |
| Request signature input | `"signature-input";req` | `sig=("@method" "@target-uri" "x-webhook-id" "content-digest");keyid="scictt:74c509cadc714ca0a7bb9f61f0957c91";created=1740398429;tag="fapi-2-request"` | The `signature-input` header from the webhook delivery request.                     |
| Request signature       | `"signature";req`       | `sig=:MEUCIQC1d6wC9rc9FCFMa738GbgxbtFFPeWdcRnL0rrfELN2MAIgW8w57eo46Fl29C5CZ6SRAl2ouq9k/jQ79AkiUVI8OsQ=:`                                                | The `signature` on the webhook delivery request.                                    |

To sign your response to a webhook, you must:

1. Build the `signature-input`, noting the values of all the headers.
2. Build the signature base.
3. Sign the signature base with your private key.

<Callout colour="blue">
  Webhook <em>responses</em> are signed, but do not require an access token or mTLS authentication.
</Callout>

## Set up and test webhook listener URLs

You can create one webhook listener for all events, or separate webhook listeners for specific events.

To manage your webhook definitions and set your webhook listener URLs for each event:

1. Sign in to the ClearBank Portal. See [Access the ClearBank Portal](./register-your-api-client#access-the-clearbank-portal) for more information.
2. From the menu, select **Institution** > **Webhook Management**.
3. Search for the webhook you want to configure and select **Edit**.
4. Enter the **URL** you want to define as your webhook listener for this webhook, and set the webhook status to **Enabled**.
5. Select **Save**.

**You must not include any sensitive information (such as API keys) in your webhook URLs.**
